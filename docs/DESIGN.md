# 行情哨兵（Market Sentinel）
## 本地行情指标监控与 Discord 通知系统 · 设计文档

> 版本：v1.0  
> 日期：2026-11-09  
> 状态：**v1.0.0 已实现；本文件作为规则语义与设计基线**  
> 数据源：OKX 公共行情（不需要 API Key）  
> 通知：Discord Webhook  
> 运行形态：本机运行的单机 Web 应用，默认地址 `http://127.0.0.1:8787`  
> 一句话：把“KDJ 到 90”“布林中轨斜率转负”“价格触及下轨”等自然语言，变成可组合、可回放、可审计的确定性规则；只做提醒和记录，不自动下单。

## 0. 先看结论

### 0.1 产品定义

这是一个**本地的指标条件监控器**，不是策略回测平台，也不是交易机器人。

它做四件事：

1. 从 OKX 订阅用户关心的品种和周期 K 线；
2. 按用户配置的布林带、KDJ、RSI、MACD、成交量等条件持续判断；
3. 当条件由“不满足”变为“满足”时，通过 Discord Webhook 发出结构化通知；
4. 把每一次触发、条件取值、发送结果保存下来，方便复盘和排错。

### 0.2 本设计最关键的 5 个口径

| # | 口径 | 默认设计 |
|---|---|---|
| 1 | 什么时候算触发 | 整条规则的判断结果**由假变真**时触发；持续满足不重复发送 |
| 2 | 用哪根 K 线 | 默认只用**已收盘 K 线**；每条规则可单独改为盘中触发 |
| 3 | “并且”是什么 | 同一时刻各条件同时成立；**不是**“A 发生后 B 再发生”的时序组合 |
| 4 | “触及下轨”怎么算 | 默认用最低价 `low <= lowerBand`，包含影线；也可改为收盘价触及 |
| 5 | 数据异常怎么办 | 暂停该规则判断，不拿旧数据发信号；恢复后重建基线，不补发旧信号 |

这五点决定了系统的行为边界，也是请优先确认的部分。

### 0.3 推荐技术形态

- **本地单进程 Web 应用**：Node.js 24 + TypeScript 后端，React + Vite 前端，SQLite 持久化。
- 浏览器访问本机地址，不做 Electron 壳；部署和调试更简单，UI 能力不受限。
- OKX WebSocket 为主、REST 对账补洞；Discord 采用本地 outbox 重试。
- 默认深色、中文、桌面优先；不引入云服务，不需要 OKX 账号或 API Key。

技术选型理由和完整架构见第 8 节。

### 0.4 本期范围

**包含：**

- 规则的新建、编辑、复制、启停、暂停、删除；
- AND/OR 嵌套组合，最多 12 个叶子条件、3 层嵌套；
- 多品种、多周期：1m / 3m / 5m / 15m / 30m / 1H / 2H / 4H / 1D；
- 布林带、KDJ、RSI、MACD、成交量；
- 收盘确认和盘中触发两种模式；
- Discord 通知、测试消息、失败重试、发送审计；
- 总览、规则、事件、设置四个主要页面；
- 规则当前状态预览、近 7/30 天信号试跑、触发点 K 线标记；
- 数据断线重连、缺口检测、代理支持、本地持久化；
- 单元测试、集成测试和本地 24 小时稳定性验收。

**不包含：**

- 自动下单、仓位管理、止盈止损执行；
- 云端部署、多用户、登录鉴权、移动端 App；
- 跨交易所比价、跨品种引用；
- “A 先发生、N 根内 B 再发生”的时序规则；
- 自定义公式/Pine Script；
- 盈利回测、收益率曲线、策略评价；
- 浏览器桌面通知、短信、Telegram。

这些不包含项不是遗漏，而是首版刻意收窄，避免把“监控器”做成“交易系统”。

## 1. 需求翻译：四个例子如何变成可执行规则

### 1.1 逐条定义

| 用户表述 | 系统条件（叶子） | 实际触发时机 |
|---|---|---|
| “15m 周期 KDJ 的 J 值到达 90” | 品种的 15m `KDJ.J >= 90` | 在 15m 收盘后，J 从 `<90` 进入 `>=90` 的第一根 |
| “5m 布林带中轨斜率变为负值” | 5m `BB.midSlope < 0` | 在 5m 收盘后，整体结果由假变真，即斜率首次进入负值区 |
| “5m 周期价格触及布林带下轨” | 5m `low <= BB.lower` | 在 5m 收盘后，该根最低价触及/跌破下轨，且规则状态由假变真 |
| “15m 中轨斜率变为正值，并且 5m 价格触及下轨” | 根组 `AND`：15m `BB.midSlope > 0` + 5m `low <= BB.lower` | 每次 5m 或 15m 收盘后检查；两个条件同时成立且整体由假变真时触发 |

### 1.2 为什么不提供单独的“上穿/下穿”操作符

首版所有叶子条件都是**状态表达式**，例如“J 当前大于等于 90”“斜率当前小于 0”。触发由整条规则的边沿检测完成：

```
上一次整体判断：false
本次整体判断：  true
→ 触发一次
```

这样设计的好处：

- “J 到达 90”和“J 上穿 90”在监控层面是同一个事件，不需要让用户区分；
- “斜率变为负值”自然等价于 `midSlope < 0` 从 false 变 true；
- 多条件组合不会因为某个叶子是“瞬时事件”而在另一周期无法对齐；
- 规则可解释、可试跑，UI 不需要暴露一套容易配错的穿越操作符。

代价是：如果某个条件已经持续为真很久，之后另一个条件才变真，系统仍会触发。这符合“同时成立”的组合语义；如果用户想要严格时序，属于后续的“序列规则”。

### 1.3 “价格触及”的准确口径

“触及布林带下轨”至少有三种常见理解，首版全部可见、默认选第一种：

| UI 名称 | 叶子条件 | 含义 |
|---|---|---|
| **最低价触及下轨（默认）** | `low <= BB.lower` | 本根 K 线的任何时刻碰到/刺穿下轨都算，包含影线 |
| 收盘价触及下轨 | `close <= BB.lower` | 只在本根收盘价位于下轨下方才成立 |
| 最低价严格跌破下轨 | `low < BB.lower` | 不把刚好相等算作触及 |

上轨同理，用 `high` / `close` 做镜像。

### 1.4 “并且”的边界

首版“并且”是**逻辑与**，检查的是同一评估时刻各条件的最新状态：

- 15m 斜率为正，可以已经持续了几根 15m；
- 5m 价格在本根触及下轨；
- 两者同时为真时触发；
- 不做“斜率转正后 3 根 5m 内必须触及”这种时序约束。

如果以后需要时序组合，新增“序列组”作为单独的规则类型，而不是把现有 AND 语义偷偷改掉。

### 1.5 多周期如何对齐

当一条规则同时引用 15m 和 5m：

- 不会把 15m 和 5m 强行重采样到同一根 K 线；
- 每个条件始终读取它自己周期**最近一根已收盘 K 线**；
- 每次任一被引用周期收盘时，重新检查整条规则；
- 同一个时间边界上如果 5m 和 15m 同时收盘，等待约 1 秒汇总，只评估一次；
- 任一条件的数据不新鲜或存在缺口，则整条规则本次不判断，不发出信号。

这样组合规则不会被错误地对齐，也不会出现“5m 已经走完三根，15m 还拿着旧值”的静默错误。

## 2. 交互与界面设计

### 2.1 信息架构

| 路由 | 页面 | 主要任务 |
|---|---|---|
| `/` | 总览 | 看连接状态、规则状态、今日触发、最近事件 |
| `/rules` | 规则 | 浏览、启停、筛选、进入编辑 |
| `/rules/new` | 新建规则 | 从模板或空白开始，组合条件并试跑 |
| `/rules/:id/edit` | 编辑规则 | 修改条件、查看当前判断、保存 |
| `/events` | 事件 | 查看触发、发送状态、失败重试 |
| `/events/:id` | 事件详情抽屉 | 查看条件快照、K 线上下文、发送记录 |
| `/settings` | 设置 | Discord、网络/代理、数据保留、诊断 |

主导航只保留四个入口。**诊断**放在设置页的折叠区和顶部连接状态入口，避免把高级运维概念放到首屏。

### 2.2 视觉语言

- **风格**：深色交易终端，信息密度较高，但留白清楚；不使用廉价霓虹和大面积渐变。
- **主背景**：`#0B0F14`；内容面板：`#111821`；浮层：`#16202B`；描边：`#253240`。
- **文字**：主文字 `#E8EEF5`，次级文字 `#8B9AAB`。
- **品牌色**：青绿色 `#2DD4BF`，只用于主按钮、焦点和品牌识别。
- **涨跌色**：涨 `#22C55E`，跌 `#EF4444`，警示 `#F59E0B`。方向不能只靠颜色表达，必须同时有文字/箭头。
- **字体**：系统中文字体（PingFang SC / Microsoft YaHei）+ 系统无衬线；所有价格、指标值、时间使用等宽字体 `ui-monospace`，便于扫读。
- **圆角**：卡片 12px，控件 8px，状态胶囊 999px。
- **动效**：120–180ms，只用于抽屉、状态切换和 toast；尊重 `prefers-reduced-motion`。
- **布局**：桌面优先，1440px 为最佳宽度；1024–1280px 自动收窄，规则编辑器从三栏变为两栏，右侧预览移到底部。
- **主题**：首版只做深色主题，不做主题切换，减少视觉验收面。

#### 顶部基础设置

| 字段 | 控件 | 默认与约束 |
|---|---|---|
| 规则名称 | 单行输入 | 必填，2–40 字；重名允许但提示 |
| 适用品种 | 多选搜索框 | 至少 1 个；从 OKX 在线品种中搜索；不同品种独立判断、独立触发 |
| 触发时点 | 分段控件 | `收盘确认`（默认）/ `盘中触发` |
| 冷却时间 | 下拉/数字 | 默认 5 分钟；0–1440 分钟 |
| 通知通道 | 只读/单选 | 首版只有一个默认 Webhook；未配置时显示“去设置” |
| 备注（可选） | 多行 | 出现在 Discord 消息和事件详情，限 200 字 |

**品种多选的含意要明确写出**：

> 多个品种分别判断、分别通知；不是要求多个品种同时满足。

#### 条件行结构

每个叶子条件由五段组成：

```
[周期] [指标大类 · 序列] [比较符] [右侧类型 · 值]        [参数] [删除]
  15m    布林带 · 中轨斜率      >         0
   5m    价格 · 最低价          ≤      指标 · 布林带下轨
```

左侧序列目录：

| 大类 | 可选序列 | 默认参数 |
|---|---|---|
| 价格 | 开盘价、最高价、最低价、收盘价 | — |
| 布林带 | 上轨、中轨、下轨、带宽、%B、中轨斜率 | 周期 20，倍数 2，均值 SMA，总体标准差，斜率窗口 1 根 |
| KDJ | K、D、J | 周期 9，K 平滑 3，D 平滑 3 |
| RSI | RSI | 周期 14，Wilder 平滑 |
| MACD | DIF、DEA、MACD 柱 | 12 / 26 / 9；柱 = DIF − DEA |
| 成交量 | 成交量、成交量均线、量能倍数 | 成交量使用计价货币成交额；均线周期 5/10/20 可选；量能倍数默认 20 周期 |

比较符只保留：`>`、`≥`、`<`、`≤`。首版不提供“等于”，因为指标浮点值做精确相等没有实际意义。

右侧支持两种类型：

1. **固定数值**：如 `90`、`0`、`1.5`；
2. **同一品种、同一周期的指标序列**：如布林带下轨、成交量均线 5、DEA。

右侧显示类型切换后，数值输入框变为指标选择器。单位提示自动变化，例如价格是 USDT、成交量是 USDT 成交额、斜率是 `%/根`。

#### 参数展开

每个条件行右侧的齿轮按钮打开参数浮层：

- 布林带：周期、标准差倍数、均线类型（首版固定 SMA）、标准差口径说明、斜率窗口；
- KDJ：周期、K 平滑、D 平滑；
- RSI：周期；
- MACD：快线、慢线、信号线；
- 成交量：均线周期、量能倍数周期。

修改参数后，条件行下方立即显示“当前值 / 数据时间”，同时更新规则摘要和试跑。参数按条件独立保存，不在规则级统一设置，避免“同一规则里的两个布林带被意外绑死”。

#### AND / OR 条件组

- 根组默认为 `AND`，可切换为 `OR`；
- 组内每一行可以是条件或子组；
- 子组有自己的 AND/OR，视觉上缩进并用左侧竖线标出层级；
- 添加条件、添加条件组、删除、上移/下移均可用鼠标和键盘；
- 最多 3 层，最多 12 个叶子条件；
- 不提供任意深的括号公式，避免把 UI 做成表达式编程器；
- 删除非空条件组需确认。

规则摘要用自然语言实时生成。例如：

> 当 15m 布林带中轨斜率（20,2，1 根）> 0，并且 5m 最低价 ≤ 布林带下轨（20,2）时；在两个周期的已收盘 K 线上判断，条件由不满足变为满足后触发；冷却 5 分钟。

#### 右侧“当前判断”

不用用户去猜当前条件是否满足，编辑器右侧实时展示：

- 每片叶子的当前值、阈值、所用 K 线的收盘时间；
- 叶子的真假状态；
- 整组表达式的真假；
- 规则当前状态（预热中 / 监控中 / 已满足 / 数据异常 / 已暂停）；
- 最近一次判断时间；
- 若数据异常，解释具体原因和修复动作。

该面板从服务端读取最近一次评估快照，不做前端重复计算，确保“界面显示的值”和“实际触发用的值”完全一致。

#### 试跑

点击“试跑”打开全屏抽屉：

- 选择回看 window：最近 7 天 / 30 天（受周期和数据量限制）；
- 显示预计触发次数、每天触发次数、最近 10 次触发；
- 显示触发点 K 线图，标记触发位置；
- 逐条展开可以看到各条件的当时取值；
- 明确标注：**只统计规则触发，不代表盈利或策略有效性**；
- 试跑不发送 Discord 消息，不写入正式事件流。

#### 保存行为

- “保存”只保存，不改变启用状态；
- “保存并启用”保存后启用；
- 保存修改会递增规则版本、重置该规则的当前满足状态、重新建立基线；
- 保存时如果表达式中存在单位不一致的软警告，显示提示但允许保存；
- 结构性错误（空规则、缺品种、缺阈值、超过层数/叶子数）阻止保存；
- 启用时如果当前条件已经满足，不立即发送历史信号；界面显示“当前已满足，等待重新进入”。

## 3. 规则模型与触发语义

### 3.1 核心对象

- **Rule（规则）**：名称、品种列表、触发模式、冷却时间、表达式树、备注、启停状态。
- **Symbol（品种）**：OKX `instId`，例如 `BTC-USDT-SWAP`。一条规则可包含多个品种，每个品种独立计算。
- **Condition（叶子条件）**：某品种某周期上的一个状态比较。
- **Expression（表达式）**：AND/OR 嵌套树。
- **RuleState（规则状态）**：每条 `规则 × 品种` 的最近一次判断、状态和数据时间。
- **Event（事件）**：一次由假变真的触发快照。
- **Delivery（投递）**：一次 Discord 发送尝试及结果。

### 3.2 表达式 JSON

以“15m 中轨斜率为正，并且 5m 最低价触及布林带下轨”为例：

```json
{
  "schemaVersion": 1,
  "name": "趋势回踩组合",
  "symbols": ["BTC-USDT-SWAP"],
  "triggerMode": "close",
  "cooldownSec": 300,
  "expression": {
    "kind": "group",
    "op": "AND",
    "children": [
      {
        "kind": "condition",
        "id": "c1",
        "timeframe": "15m",
        "left": {
          "series": "bb.midSlope",
          "params": { "length": 20, "mult": 2, "slopeWindow": 1 }
        },
        "cmp": "gt",
        "right": { "type": "number", "value": 0 }
      },
      {
        "kind": "condition",
        "id": "c2",
        "timeframe": "5m",
        "left": {
          "series": "price.low"
        },
        "cmp": "lte",
        "right": {
          "type": "series",
          "series": "bb.lower",
          "params": { "length": 20, "mult": 2 }
        }
      }
    ]
  }
}
```

约定：

- 所有序列引用都隐含“当前规则的当前品种 + 当前条件周期”，首版不支持跨品种引用；
- `right` 的指标序列与 `left` 使用同一品种、同一周期；
- 指标参数随条件保存，保证历史事件可解释；
- 事件记录规则版本和序列化后的条件快照，规则被修改后历史不变。

### 3.3 叶子条件目录

| 序列 key | UI 名称 | 单位/值域 | 说明 |
|---|---|---|---|
| `price.open/high/low/close` | 开盘/最高/最低/收盘 | 报价货币 | OKX K 线字段 |
| `bb.upper/middle/lower` | 上轨/中轨/下轨 | 报价货币 | SMA + kσ |
| `bb.bandwidth` | 带宽 | % | `(upper−lower)/middle×100` |
| `bb.percentB` | %B | 无量纲 | `(close−lower)/(upper−lower)` |
| `bb.midSlope` | 中轨斜率 | %/根 | 中轨在 k 根内的归一化变化 |
| `kdj.k/d/j` | K / D / J | 点 | J 可超出 0–100 |
| `rsi.rsi` | RSI | 0–100 | Wilder |
| `macd.dif/dea/hist` | DIF / DEA / 柱 | 报价货币 | 柱 = DIF − DEA |
| `volume.quote` | 成交量 | 报价货币成交额 | OKX `volCcyQuote` |
| `volume.ma` | 成交量均线 | 报价货币成交额 | 默认 5 / 10 / 20 可选 |
| `volume.ratio` | 量能倍数 | 倍 | 当前成交量 / 成交量 SMA(N) |

比较符：`gt`、`gte`、`lt`、`lte`，分别映射 UI 的 `>`、`≥`、`<`、`≤`。

### 3.4 评估算法

伪代码：

```text
onCandleClosed(instId, timeframe, bar):
    saveClosedBar(bar)
    for each enabled rule containing instId and timeframe:
        scheduleEvaluate(rule, instId, delay=1s, coalesce=true)

evaluate(rule, instId):
    leaves = flatten(rule.expression)

    for leaf in leaves:
        bars[leaf.timeframe] = latestClosedBar(instId, leaf.timeframe)
        if bars[leaf.timeframe] is missing:
            markRuleDegraded("missing bar")
            return
        if not isFresh(bars[leaf.timeframe], now):
            markRuleDegraded("stale bar")
            return
        if not hasContinuousHistory(instId, leaf.timeframe, requiredLookback):
            try backfill()
            if still gap:
                markRuleDegraded("data gap")
                return
        leaf.value = computeSeries(leaf).at(latest bar)
        leaf.truth = compare(leaf.value, cmp, rightValue)

    current = evalTree(rule.expression, leaves)

    if ruleState.lastTruth is NULL:          // 冷启动/启用/编辑后
        ruleState.lastTruth = current
        ruleState.status = current ? "SATISFIED" : "ARMED"
        return

    if ruleState.lastTruth == false and current == true:
        if now - ruleState.lastTriggerAt >= cooldown:
            createEventAndEnqueueDelivery(snapshot)
            ruleState.lastTriggerAt = now
            ruleState.status = "SATISFIED"
        else:
            logSuppressedByCooldown()
    else:
        ruleState.status = current ? "SATISFIED" : "ARMED"

    ruleState.lastTruth = current
    ruleState.lastEvalAt = now
```

关键点：

- **先计算全部叶子**，不做短路。即使 AND 的第一个条件为假，也要保存其余条件的当前值，供 UI 和事件快照使用。
- **不把“瞬时事件”埋在叶子比较里**。真假变化由整体表达式负责，逻辑一致。
- **数据不可用时返回 UNKNOWN**，不把缺失值当 false 或 0。
- **只在变为 true 时创建事件**。持续 true 不重复创建。
- 冷却只影响触发后的通知；冷却中被压制的边沿仍会更新状态，不会过一会儿补发。
- 同一 `rule × symbol × K线` 通过数据库唯一键兜底，WS 重复推送不会产生重复事件。

### 3.5 多周期对齐细节

- 收盘确认模式下，每个叶子读取自己的最近一根已收盘 K 线。
- “最近一根”以 OKX 返回的 K 线时间戳为准；不在本地重新合成更高周期。
- 同一时间边界上，多个周期可能同时收盘；等待 1 秒让消息归拢，然后只评估一次。
- 如果 5m 和 15m 在同一秒收盘，事件价取最短引用周期的收盘价，事件快照同时保留两个周期各自的 OHLC。
- 若更高周期数据缺失，即使低周期刚收盘，也整条规则不判断。
- 1D 的日界以 OKX 时间戳为准。实测 OKX 的 1D 边界按 UTC+8 日界返回（16:00 UTC，即北京时间 00:00），不得按本地 UTC 零点自行切分。

### 3.5.1 盘中触发模式（可选，默认关闭）

盘中模式不是另一套判断逻辑，只是把“最近一根已收盘 K 线”换成“最新一根 K 线（含未收盘）”，其余边沿、冷却、去重规则保持一致。

- **评估频率**：OKX WebSocket 推送当前 K 线变化时触发；同一条规则最多每 500ms 计算一次，避免高频推送造成 UI 和 CPU 抖动。
- **数据口径**：组合规则中，15m 条件也使用当前未收盘的 15m K 线。也就是说，15m 的指标值会随着价格变化而重绘。这是为了让“盘中触发”真正及时，不把高周期拖到收盘才更新。
- **触发去重**：同一 `规则 × 品种 × 最短引用周期的 K 线开盘时间` 最多一个事件。例如 15m + 5m 组合按 5m 的当前 K 线去重；仅有 15m 条件则按 15m 去重。
- **收盘处理**：盘中已经发送后，到收盘不重复发送；系统在事件详情中更新“收盘是否确认”。如果收盘时表达式不再为真，事件标记为“收盘未确认”。不编辑已发出的 Discord 消息，避免依赖 Webhook 的消息编辑能力。
- **消息标记**：Discord 标题或正文必须有醒目的“盘中触发 · 未收盘，可能失效”；事件列表使用 `盘中` 标签。
- **数据要求**：仍然要求历史数据连续、指标预热完成；未收盘 K 线缺失或连接中断时不判断。
- **风险提示**：UI 从“收盘确认”切到“盘中触发”时显示一次解释；这是可能产生假信号的模式，建议先用试跑观察触发频率。

### 3.6 新鲜度与缺口

- 每个周期都维护“当前未收盘 K 线”和“最近已收盘 K 线”。
- 叶子数据新鲜，指最近已收盘 K 线正是按交易所边界应有的上一根；允许收盘后最多 10 秒的传输宽限。
- 指标回看窗口内不允许有缺口。发现缺口时先用 REST 补洞；补不齐则规则进入“数据异常”，不判断。
- 如果 WebSocket 断开并错过了已收盘 K 线，重连后补数据，但**不补发这些旧信号**；对受影响规则重建基线，在界面显示“已恢复，等待下一次重新满足”。
- 应用启动、规则启用、规则修改后，均先建立基线，不补发触发前的历史状态。

### 3.7 判定和通知的生命周期

| 场景 | 行为 |
|---|---|
| 首次启动，条件已满足 | 建立基线，标记“已满足”，不发消息 |
| 规则启用时已满足 | 同上 |
| 条件保持满足 | 不重复；界面显示“已满足” |
| 条件先假后真 | 创建事件，进入发送队列 |
| 冷却期内再次假→真 | 不发送；日志记录被冷却抑制 |
| 规则被编辑 | 版本 +1，状态重置并重建基线，不发旧状态 |
| 规则被暂停 | 不评估；恢复时重建基线 |
| 软件重启 | 状态从数据库恢复；补数据但不补发历史；待发送队列继续发送 |
| 数据断线/缺口 | 规则暂停判断；恢复后重建基线，不补发 |
| Webhook 不可用 | 事件照常记录；投递重试；界面显示失败 |

### 3.8 多品种语义

- 一条规则配置多个品种时，每个品种各有一份 `RuleState`；
- 每个品种可以单独触发，Discord 消息分别发送；
- 冷却也按“规则 × 品种”独立计时；
- UI 的规则状态展示需区分“哪些品种处于异常”，不能只给一个笼统的红点；
- 首版不支持“多个品种同时满足才触发”。这属于跨品种组合，后续单列。

### 3.9 校验规则

保存时校验：

- 至少 1 个品种、至少 1 个有效叶子；
- 叶子不超过 12 个，嵌套不超过 3 层；
- 每个条件有时间周期、序列、比较符和右值；
- 右值为数值时必须是有限数；为指标序列时必须与左侧同周期；
- 指标参数在允许范围内（如周期 2–500，倍数 0.1–10）；
- 规则名 2–40 字；
- 冷却 0–1440 分钟；
- 品种必须存在于 OKX 在线品种列表，且未被下线；
- 数据预热时长不足时允许保存，但禁止启用并提示“历史数据不足”。

软警告（允许保存但提示）：

- 左侧和右侧单位类别不同（例如价格和成交量比较）；
- 阈值取在指标的常规值域之外（例如 RSI > 150）；
- 条件组里同时出现明显重复的条件；
- 7 天试跑预计触发超过 50 次，提示提高阈值或增加冷却。

### 3.10 规则试跑（不是盈利回测）

试跑使用与线上完全相同的规则求值器，只替换数据来源和通知出口：

- 读取最近 7 天或 30 天的历史 K 线，并额外加载指标预热所需的 K 线；
- 按所有被引用周期的时间顺序逐根推进，每个评估点只使用当时已收盘的数据；
- 和线上一样做多周期对齐、新鲜度、缺口和冷却；
- 起点建立基线，不把窗口开始前的已满足状态当成触发；
- 输出触发次数、每日次数、最近触发列表和图表标记；
- 不发送 Discord，不写入正式事件表；
- 明确标注“信号试跑/触发统计，不计算盈亏”。

限制：

- 30 天为上限；1m 周期最多回看 7 天，避免请求和数据量过大；
- 历史 REST 请求可能受限，试跑显示进度和取消按钮；
- 试跑结果是历史模拟，不代表未来表现。

## 4. 指标定义

指标实现必须版本化。所有公式在首次发布时冻结为 `indicators-v1`，事件记录该版本；后续修改公式需要升版本，避免历史不可解释。

### 4.1 布林带（BB）

默认参数：`N=20`，`k=2`，均线使用 SMA，标准差使用**总体标准差**（除以 N）。

\[
M_t = \frac{1}{N}\sum_{i=0}^{N-1} C_{t-i}
\]

\[
\sigma_t = \sqrt{\frac{1}{N}\sum_{i=0}^{N-1}(C_{t-i} - M_t)^2}
\]

\[
U_t = M_t + k\sigma_t,\quad L_t = M_t - k\sigma_t
\]

衍生序列：

- **带宽**：`(U_t - L_t) / M_t × 100`，单位 `%`。
- **%B**：`(C_t - L_t) / (U_t - L_t)`。带宽为 0 时返回空值，不当作 0。
- **中轨斜率**：默认窗口 `s=1`：

\[
\text{midSlope}_t = \frac{M_t - M_{t-s}}{M_{t-s}} \times 100 \div s
\]

单位 `%/根`。正负号与常见“中轨方向”直觉一致；除以 s 后不同斜率窗口仍可比较。UI 中显示为“中轨斜率（%/根）”。

### 4.2 KDJ

默认参数：`N=9`，K 平滑 `m1=3`，D 平滑 `m2=3`。

\[
RSV_t = 100 \times \frac{C_t - LLV_t}{HHV_t - LLV_t}
\]

其中 `HHV_t = max(high, N)`，`LLV_t = min(low, N)`。当 `HHV=LLV` 时，`RSV` 取 50，避免除零。

\[
K_t = \frac{m_1-1}{m_1}K_{t-1} + \frac{1}{m_1}RSV_t
\]

\[
D_t = \frac{m_2-1}{m_2}D_{t-1} + \frac{1}{m_2}K_t
\]

\[
J_t = 3K_t - 2D_t
\]

初值 `K_0 = D_0 = 50`。J 可以小于 0 或大于 100，系统不截断。UI 显示 K/D/J 三值，条件可直接选 J。

### 4.3 RSI

默认参数 `N=14`，使用 Wilder 平滑。

- 初始平均涨幅/跌幅：前 N 个价格变化的算术平均；
- 之后：`avgGain = (avgGain × (N−1) + gain) / N`，跌幅同理；
- `RS = avgGain / avgLoss`；
- `RSI = 100 − 100/(1+RS)`；
- 若 `avgLoss=0` 且 `avgGain>0`，RSI 记为 100；
- 若两者都为 0，RSI 记为 50，避免横盘被误判为极度超买。

### 4.4 MACD

默认参数：快线 12、慢线 26、信号线 9。

- EMA 采用标准递推：`α=2/(N+1)`，首个 EMA 用前 N 个收盘价的 SMA 初始化；
- `DIF = EMA(close,12) − EMA(close,26)`；
- `DEA = EMA(DIF,9)`；
- **MACD 柱 = DIF − DEA**，不乘 2。

UI 参数浮层中必须写出“柱 = DIF − DEA”。这样不会与“柱 = 2 × (DIF − DEA)”的软件产生视觉差异却难以发现。

### 4.5 成交量

- 使用 OKX K 线的 `volCcyQuote` 字段，即**报价货币成交额**。对 `BTC-USDT-SWAP` 为 USDT 成交额，而不是合约张数。
- 这样既跨品种可比，也不受合约面值影响。
- 成交量均线：`SMA(volume, N)`，默认 N=20，UI 可直接选择 5/10/20。
- 量能倍数：`volume / SMA(volume, N)`，默认 N=20；分母为 0 时返回空值。
- 盘中的成交量是未完成 K 线的部分值，只应在盘中模式下比较，消息中要标注“盘中”。

### 4.6 预热、空值与精度

- 最少加载 300 根已收盘 K 线；指标未达到最小窗口或数据不连续时，不进行判断。
- 指标计算中的空值（NaN/null）视为“不可判断”，对应规则进入数据异常，不得当作 false、0 或 50。
- 比较使用 JavaScript 双精度浮点；阈值不做隐式四舍五入。显示层可按品种精度格式化，但判断使用原始值。
- 指标参数、公式版本、K 线 `openTime` 一起写入事件快照。
- 默认时间周期：`1m, 3m, 5m, 15m, 30m, 1H, 2H, 4H, 1D`。暂不提供周线/月线，避免日界与展示复杂化。

## 5. OKX 数据层

### 5.1 当前接口（2026-11 已核验）

| 用途 | 端点 |
|---|---|
| REST 基址 | `https://openapi.okx.com`（`https://www.okx.com` 也仍可用） |
| 最近 K 线 | `GET /api/v5/market/candles?instId=...&bar=...&limit=...` |
| 历史 K 线（试跑/补洞） | `GET /api/v5/market/history-candles?instId=...&bar=...&after/before=...` |
| 品种列表 | `GET /api/v5/public/instruments?instType=SPOT/SWAP` |
| 服务器时间 | `GET /api/v5/public/time` |
| WebSocket K 线 | `wss://ws.okx.com/ws/v5/business`，订阅 `candle5m` / `candle15m` 等 |

**当前端点不使用 `:8443`。** OKX 已于 2026-10-31 停止公网 8443 WebSocket 接入，业务频道统一走 443，路径仍为 `/ws/v5/business`。配置中只保存主机和路径，不写死端口。

K 线返回格式（已实测验证）：

```
[ts, open, high, low, close, vol, volCcy, volCcyQuote, confirm]
```

- `confirm=0`：未收盘；
- `confirm=1`：已收盘；
- 成交量指标使用 `volCcyQuote`；
- K 线时间戳 `ts` 是开盘时间；
- 收盘时间 = `ts + timeframe`，但 1D 的日界以交易所实际返回的时间戳为准。

### 5.2 数据获取策略

1. **启动/新增品种周期**：REST 拉取最近 300 根，过滤 `confirm=1`，排序去重，做连续性检查。
2. **实时**：为所有启用规则涉及到的 `品种 × 周期` 建立一条或多条 Business WebSocket 连接，按 `candle{tf}` 频道订阅。
3. **对账**：WebSocket 为主；定时（默认每 60 秒）或用收盘后延迟检查，发现当前周期没有按时收到已收盘 K 线时，触发 REST 拉取。
4. **回填**：发现缺失的中间 K 线，使用 history-candles 分页补齐；无法补齐则规则数据异常。
5. **通知**：只有具备新鲜、连续数据的评估才允许产生事件。

### 5.3 WebSocket 连接管理

- 连接 OKX 公共业务频道，无需鉴权。
- 订阅按 `品种 + 周期` 去重，避免同一条 K 线被多个规则重复订阅。
- 应用层 `ping` / `pong` 定时心跳；连续多个周期无消息或心跳失败则重连。
- 重连采用指数退避 + 抖动（约 1s → 60s），避免网络异常时持续冲击。
- 重连成功后重新发送当前所有订阅，先做 REST 对账，再恢复评估。
- 收到重复的 `confirm=1` K 线时，按 `(instId, timeframe, openTime)` 去重。
- 首次订阅时可能出现历史快照或首个未完成 K 线，必须自行过滤，不用未确认数据建立正式基线。
- 代理通过 WebSocket 代理 agent 建立；代理失败时错误要能出现在诊断页，而非静默重试。

### 5.4 数据状态

每个 `品种 × 周期` 维护：

- `CONNECTING`：还没有足够数据；
- `HEALTHY`：当前 K 线和最近收盘 K 线正常；
- `STALE`：最近 K 线超过允许延迟未更新；
- `GAP`：回看窗口存在缺口，补洞失败；
- `DISCONNECTED`：数据源连接中断。

每个规则在自身状态之上汇总：

- 任一叶子依赖的数据非 HEALTHY → 规则进入“数据异常”；
- WebSocket 断开但尚未错过收盘 K 线 → 可以短暂 `DEGRADED` 但不必马上报警；
- 一旦错过或需要重建，恢复时**不补发旧信号**。

### 5.5 限流、退避和网络

- 所有 OKX REST 请求走统一的最小间隔和并发上限，不因多条规则叠加而无限发请求。
- `429` / `5xx` / 网络错误采用指数退避；`4xx` 参数错误不做无意义重试。
- 代理为可选配置，REST 与 WebSocket 共用同一代理设置；Discord 可单独选择是否走代理。
- 启动时请求 `/public/time`，记录本机与 OKX 服务器时间差；UI 显示漂移。本应用只读公共接口，不涉及签名时间窗口，但漂移会影响新鲜度判断的可信度。
- 不绕过 TLS 校验；不提供“忽略证书错误”按钮作为常规选项。

### 5.6 品种支持范围

首版优先支持：

- OKX 现货（SPOT）；
- USDT 本位永续（SWAP）。

其他 OKX 类型（交割、币本位、期权）虽然底层 `instId` 可能可用，但不列入首版验收范围。品种搜索只显示 `state=live` 的工具，并在规则保存时再次校验，避免规则配置到已下线品种。

## 6. Discord 通知

### 6.1 配置与安全

- 只支持 Discord Webhook，不需要 Bot Token。
- Webhook URL 是秘密：保存后 API 不返回完整 URL，UI 只显示尾部 4 位；日志必须脱敏。
- 只允许 `https://discord.com/api/webhooks/...`（以及 Discord 官方备用域名），避免被当作任意 URL 请求器/SSRF 跳板。
- 发送请求带 `allowed_mentions: { "parse": [] }`，禁止 `@everyone`、角色和用户被规则名/备注意外触发。
- Webhook 配置保存在本地数据库，数据库文件权限 `0600`。首版不做应用层加密，依赖本机磁盘加密；文档中明确说明这一点。
- 首版只有一个通知通道。多 Webhook / 每规则指定频道列入后续版本。

### 6.2 消息结构

使用 Discord Embed，单条消息最多一个 embed，控制长度，保证不因字段过长被 Discord 拒绝。

示例：

```
┌──────────────────────────────────────────────┐
│ 📡 触发 · BTC-USDT-SWAP                      │
│ 5m / 15m · 趋势回踩组合                      │
│                                              │
│ 触发时间   2026-11-09 14:50:03 CST           │
│ 触发价     74,188.0（5m 收盘）               │
│ 触发模式   收盘确认                          │
│                                              │
│ 条件快照                                     │
│ ✓ 15m 布林中轨斜率  +0.031%/根  > 0          │
│ ✓ 5m 最低价         74,181.5   ≤ 74,220.0   │
│                                              │
│ 事件 ID    evt_01J...                        │
│ OKX 公共行情 · 仅供信息参考，不构成投资建议     │
└──────────────────────────────────────────────┘
```

字段规则：

- 标题包含“触发”和品种；
- 规则名、周期、触发模式、时间必备；
- 条件快照每片叶子一行：真值、周期、指标、实际值、比较符、阈值；
- 事件 ID 便于和本地日志对应；
- 若为盘中触发，醒目标注“盘中触发 · 未收盘，可能失效”；
- 不附本地 `127.0.0.1` 链接，因为 Discord 消息可能在手机上查看，本地链接不可达；
- 不在消息中默认 @ 任何人。

### 6.3 投递流程

```
规则触发
  → SQLite 事务写入 event + delivery（pending）
  → 投递 worker 取 pending
  → 串行调用 Discord（同一 Webhook 最小间隔）
  → 2xx：标记 sent，记录 discord message id
  → 429：按 Retry-After 等待后重试
  → 网络错误 / 5xx：指数退避重试
  → 4xx（除 429）：标记 failed，不再自动重试
  → 超过最大次数：标记 dead，UI 可手动重试
```

- Worker 在应用重启后继续处理 pending / retry 状态。
- 同一事件不会因为 WS 重复、应用重启而再次进入队列；靠 `event_id` 唯一约束保证。
- Discord Webhook 不支持真正的幂等键。若发送请求超时但 Discord 已接收，重试可能产生一条重复消息。这是外部系统限制，系统需要在消息中带事件 ID，并在设计上接受“极少数网络模糊态可能重复”。
- 进程内对同一 Webhook 串行发送，避免触发密集时自我限流；队列长度、最近错误在诊断页可见。

### 6.4 测试消息

设置页的“发送测试消息”：

- 使用固定的非业务模板；
- 明确标注“这是一条测试消息”，不会计入事件页；
- 显示 HTTP 状态、耗时、失败原因；
- 测试成功不代表规则配置正确，只代表 Webhook 和网络通。

规则编辑器的“发送测试通知”会使用当前规则的示例值渲染一条预览，但同样不会写成正式事件，也不代表真实触发。

## 7. 系统架构

### 7.1 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js 24 | 本机已具备；原生支持 fetch、WebSocket、SQLite，减少额外环境 |
| 后端 | TypeScript + Fastify | 轻量、类型完整、便于提供 REST 和静态文件 |
| 前端 | React + TypeScript + Vite | 组件化、开发反馈快、适合复杂条件编辑器 |
| 图表 | ECharts | K 线、指标叠加、触发放大标记成熟 |
| 样式 | 自建 CSS design tokens + 轻量组件 | 不被现成组件库的默认视觉限制，保持一致密度 |
| 持久化 | SQLite（WAL） | 单机可靠、无需数据库服务；Node 24 内置 `node:sqlite`，不引入原生扩展 |
| 实时 UI | Server-Sent Events（SSE） | 单向状态推送足够；比浏览器 WebSocket 简单，断线自动重连 |
| 测试 | Vitest + Playwright | 规则/指标单测 + 浏览器端到端 |

不选 Electron 的原因：用户已有浏览器；本地 Web 应用不需要安装壳，调试、升级和自动化测试成本更低。若后续需要开机自启和系统托盘，再单独加启动器，不改变核心架构。

```
│  Event Store（SQLite WAL）                                      │
│     └── Outbox / Delivery Worker                               │
│             └── Discord Webhook（HTTPS，可走代理）              │
│                                                                │
│  Static UI（构建后的 React 资源）                               │
└────────────────────────────────────────────────────────────────┘
```

### 7.3 单进程与并发

- 一个 Node 进程承载 API、行情、规则引擎和投递 worker。
- SQLite 单写者，使用 WAL 模式；所有写操作短事务。
- 行情推送和事件处理在内存中排队，指标计算尽量 O(窗口) 或使用缓存，不对 300 根 K 线做不必要的全量重算。
- 同一条规则同一时间只允许一个评估任务，防止同一根 K 线并发评估产生重复事件。
- 发送队列独立于行情评估；Discord 挂掉不影响行情记录和后续判断。

### 7.4 数据模型

```text
rules
  id, name, enabled, symbols_json, trigger_mode, cooldown_sec,
  expression_json, note, version, created_at, updated_at, archived_at

rule_states
  rule_id, symbol, rule_version, last_truth, last_eval_at,
  last_trigger_at, status, detail_json,
  PRIMARY KEY(rule_id, symbol)

events
  id, rule_id, rule_name_snapshot, rule_version, symbol,
  trigger_mode, trigger_bar_ts, trigger_at, price,
  expression_json, conditions_json, close_confirmed,
  created_at
  UNIQUE(rule_id, symbol, trigger_bar_ts)

deliveries
  id, event_id, status, attempts, next_attempt_at,
  last_http_status, last_error, external_message_id,
  created_at, updated_at
  UNIQUE(event_id)

candles
  inst_id, timeframe, open_ts, open, high, low, close,
  vol, vol_ccy, vol_ccy_quote, confirm, updated_at
  PRIMARY KEY(inst_id, timeframe, open_ts)

settings
  key, value, updated_at
```

说明：

- 规则删除采用软删除（`archived_at`）或删除后保留事件名快照；事件永远保留上下文。
- 事件表保存 `rule_name_snapshot`、条件快照、规则版本，避免规则修改后历史无法解释。
- 唯一键使用 `rule_id + symbol + trigger_bar_ts`，编辑规则版本也不允许同一根 K 线重复建事件。
- 冷却被抑制的触发写应用日志，不写事件表，避免事件页被大量“未发送”污染。
- K 线缓存按周期分层保留，至少覆盖试跑窗口；1m 默认只保留 7 天，较大周期保留更久。
- 事件默认保留 90 天，可在设置中调整。

## 8. 可靠性、安全与性能

### 8.1 可靠性设计

- 行情与通知解耦：Discord 失败不影响规则评估，事件和重试队列持久化。
- 事件和投递在同一个 SQLite 事务中落库，避免“事件存在但没有发送任务”或相反情况。
- 幂等：K 线按时间戳去重，规则事件按 `rule × symbol × bar` 唯一，投递按 `event` 唯一。
- 冷却在规则级别执行，服务重启后仍然有效。
- 数据缺口不猜测、不插值、不使用旧值硬判断。
- 启动时如果 SQLite schema 需要升级，先备份数据库再迁移；迁移失败拒绝启动，不带着半个 schema 运行。
- 退出时优雅关闭 WS、等待在途请求、关闭数据库。

### 8.2 安全边界

- 默认只监听 `127.0.0.1`，不暴露局域网。
- Webhook 和代理凭据不回传前端、不写日志、不出现在诊断导出中。
- 只允许 Discord 官方 Webhook 域名，避免 SSRF 和任意外发。
- 允许的 Discord mentions 为空，避免通知变成 @everyone 骚扰。
- API 只接受同源 JSON 请求；校验 `Origin`，不配置宽松 CORS。
- 本地应用没有账号体系；如果未来允许局域网访问，必须增加鉴权，不能直接改监听地址。
- 用户输入在 React 中自动转义；Discord 消息中对规则名/备注做长度限制和 Markdown 安全处理。
- 不请求、不存储 OKX API Key；本系统只能读公共行情。

### 8.3 性能目标

- 空闲内存占用目标 < 250 MB，常规 CPU < 2%。
- 20 条规则、5 个品种、3 个周期的组合下，收盘后的评估在 1 秒内完成。
- 首屏加载 < 2 秒（本地资源），规则编辑器交互无明显卡顿。
- Discord 发送队列与前端 SSE 不因单条消息失败阻塞。
- 指标缓存按 `品种 + 周期 + 指标 + 参数` 键复用；不会因多条规则重复拉同一份 K 线。

这些是设计目标，会在本地 24 小时验收中记录实际结果。

### 8.4 运维与日志

- 日志写入本地滚动文件，默认单文件 10 MB，保留 5 份。
- 记录连接事件、重连、数据缺口、规则状态变化、事件创建、投递尝试；不记录 Webhook 完整 URL。
- 诊断页显示最近错误，不要求用户去翻日志才能知道为什么没收到消息。
- 提供导出诊断包（配置脱敏 + 最近日志 + 数据健康快照），便于后续排查。
- 进程崩溃后重启由用户手动完成；首版不自动安装 launchd/计划任务。文档说明如何保持应用常驻。

### 8.5 已知限制（必须接受）

1. 只有本机运行时才会监控；电脑睡眠、退出应用期间不会产生通知。
2. 使用 K 线 OHLC 和最新收盘价，不是逐笔数据；“触及”只保证在已收盘 K 线的最高/最低价范围内发生过。
3. 单交易所数据源；OKX 异常时无法判断。
4. Discord Webhook 不提供端到端幂等；极端网络超时可能导致重复消息或延迟。
5. 组合规则是同时满足，不是时序组合。
6. 首版不做盈利回测，不评价规则好坏。
7. 盘中触发可能重绘（K 线未收盘），消息会明确标注，默认关闭。
8. 应用重启和长时间断线后不会补发旧信号，只重建基线；这是为了避免把过期信号当成实时提醒。

## 11. 需要你确认的默认口径

请重点确认以下 8 项。若都同意，回复“按设计开发”即可；如需调整，直接指出编号。

1. **触发语义**：整条规则由“不满足”变“满足”时提醒一次，持续满足不重复；默认冷却 5 分钟。
2. **收盘 vs 盘中**：默认只用已收盘 K 线；每条规则可选“盘中触发”，盘中消息会明确标注“可能失效”。
3. **组合语义**：首版“并且”是同时成立，不是“A 发生后 N 根内 B 发生”的时序组合。
4. **触及口径**：默认用最低价/最高价（包含影线）判断触及；可切换为收盘价口径。
5. **技术形态**：本地 Web 应用（Node 24 + React + SQLite），浏览器访问 `127.0.0.1:8787`，不做 Electron 客户端。
6. **首版范围**：包含规则试跑和 K 线触发标记；只支持一个 Discord Webhook；品种优先支持 OKX 现货和 USDT 永续。
7. **默认品种**：模板默认 `BTC-USDT-SWAP`，可改为任意 OKX 在线品种；不预置 ETH 规则。
8. **界面风格**：中文、深色、桌面优先，首版不做浅色主题和移动端专门适配。

### 确认后的开发前置

- 你提供 Discord Webhook URL（可稍后在设置页配置，不影响开发）；
- 如果需要通过代理访问 OKX/Discord，确认代理地址；本机实测 `http://127.0.0.1:7890` 当前可用；
